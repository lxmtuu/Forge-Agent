## Completed: harden fetch_url redirects and DNS handling

- Automatic HTTP redirects are disabled. Each hop is validated before the next request, with a limit of five redirects. URL credentials and hosts whose DNS answers include a non-public address are rejected.
- The request connects to a validated IP address rather than resolving the hostname a second time. The original hostname is preserved in the Host header and through HTTPX's documented `sni_hostname` extension for TLS verification. Environment proxies are disabled for this tool so they cannot independently resolve the target. This is a compatibility change for proxy-only installations and environment-provided certificate configuration.
- The validated IP is selected from DNS results; only the first is attempted, so an unreachable first address can cause a failure even if another would work. A separate HTTP client per hop avoids reusing a TLS connection for a different hostname. DNS resolution has a wait timeout, but the underlying resolver thread may continue until the OS call completes.
- `tests/test_fetch_security.py` covers private redirects, mixed public/private DNS answers, pinned IP and original Host/SNI, IPv6, redirect limits, public redirects and credential rejection. A local TLS test verifies actual Host/SNI and certificate hostname validation; it substitutes loopback for the resolver deliberately and is not an external-network security test. The remaining network cases use fake DNS and an HTTPX mock transport.
- **Limits:** this is not a complete network isolation guarantee. Unusual routing, translated addresses, compromised DNS/CA, other HTTP clients and deployment-specific egress must be assessed separately; use network-level egress restrictions. Response streaming was subsequently bounded as described in the fetch-output section below. No full Internet TLS/proxy or Windows/macOS test was performed.
- HTTPX documentation for the request extension: https://www.python-httpx.org/advanced/extensions/#sni_hostname

## Completed: background output wraparound and pagination

- The background buffer now maintains an absolute base offset and read cursor. If unread bytes are evicted from the 60 KB buffer, the next read reports the number of bytes lost; output is still irretrievably lost when a producer outruns the bounded buffer.
- A view consumes at most 4,000 bytes and reports remaining bytes rather than silently discarding everything beyond the view limit. Subsequent checks drain the remainder. UTF-8 sequences split at a view boundary or arriving in separate chunks are held until complete while the task is running.
- The initial and subsequent `render` calls now both consume unread data. A task has one shared in-memory cursor; independent multi-reader cursors, persistence across restarts and complete lossless log retention are not provided. Status may be complete while output remains to be read.
- Six tests in `tests/test_background_output.py` cover wraparound, explicit loss reporting, paginated reads, UTF-8 boundaries and a real local subprocess producing more than 60 KB. Before the change, the five initial tests reproduced missing markers or silent loss; the subprocess integration test was added afterward.
- POSIX process-group cleanup and fetch/foreground buffering are addressed below; complete process-tree termination and Docker container cleanup remain unresolved.

## Completed: bounded foreground command output

- Foreground subprocess stdout and stderr are drained in chunks, retaining at most 12,000 output bytes in the application buffer while continuing to read and discard excess to avoid blocking a verbose child. `truncated` indicates discarded bytes; normal exit status remains available. The limit applies to captured command bytes, not metadata, decoding overhead, asyncio buffers or the child process memory.
- Timeout returns retained partial output and truncation status; cancellation propagates. Cleanup was subsequently improved for POSIX process groups as described below. Neither path guarantees termination of all descendants or Docker containers, and escaped descendants can outlive the bounded cleanup wait.
- UTF-8 decoding avoids emitting a replacement character solely because truncation cuts a multibyte sequence; invalid source bytes are still decoded with replacement. The omitted partial character counts toward the byte cap. Truncation messages and other metadata are outside that cap.
- Seven tests in `tests/test_foreground_output.py` cover cap boundaries, multibyte output and split characters, timeout partial output, stderr/nonzero exit, mocked cancellation cleanup, and a real 8 MB output stream. The large-output regression measures peak Python allocations in the parent with `tracemalloc` (less than 4 MB), not total RSS or child/system memory. The sandbox subprocess mock was updated for streaming.
- **Limits:** this is not a system-wide memory limit, rate limit, complete process-tree cleanup or Docker cleanup guarantee. The process can still consume CPU, disk, and its own memory; other output paths require independent review; fetch response bodies are addressed below. Linux/Python 3.13 was tested; Windows/macOS and real Docker were not.

## Completed: bound fetch response retention

- `fetch_url` requests `Accept-Encoding: identity` and reads the final response incrementally, retaining at most 128,000 body bytes before text/HTML extraction. It closes the response after detecting excess, without downloading the rest. The existing 20,000-character display limit remains separate. An explicit message distinguishes an input byte-limit truncation; the total original page length is not claimed.
- Redirect and rejected binary response bodies are not read. Every redirect is still independently validated and pinned as described above. Responses with non-identity `Content-Encoding` are rejected before reading or decompression, including servers that ignore the identity request: this prevents a compressed expansion bomb but is a compatibility change for compression-only servers. Charset decoding retains HTTPX's selected encoding, with incomplete trailing sequences held back on input truncation.
- Eight regressions in `tests/test_fetch_output.py` cover large streamed responses, early close, redirects, binary and compressed rejection, charset and request headers, exact byte boundary, HTML/UTF-8 boundary, and a real local HTTP response larger than the cap. The local test deliberately substitutes loopback for the public-address resolver; it does not test external egress or SSRF isolation. The remaining streaming cases use HTTPX's mock transport.
- **Limits:** the bound applies to retained response body bytes, not all HTTP library buffers, headers, individual transport chunks, decoded text, HTML processing, total process RSS, or concurrent requests. HTTPX read timeout is an inactivity timeout; a separate cooperative overall deadline is now applied, as described below. TLS, DNS, network security and platform limitations described above remain. Compression is deliberately unsupported rather than safely streamed.

## Completed: POSIX foreground process-group cleanup

- On POSIX, foreground shell and Docker-client launches now start in a new session. On timeout or caller cancellation the executor sends SIGKILL to that new process group, including members still present after the original group leader exits, and briefly drains/reaps the direct process. If sending the group signal fails with an OS error, it attempts to kill the direct process. On non-POSIX systems it retains the previous direct-process kill behavior. Starting a new session changes terminal/session and signal behavior for foreground commands.
- Four Linux/POSIX integration regressions in `tests/test_foreground_process_group.py` run real local subprocesses: timeout and cancellation of a shell spawning a descendant, a pipe-holding descendant after the leader exits, and ordinary successful execution. The first two reproduced surviving descendants before the change; leaked baseline test processes were explicitly cleaned up. The earlier mocked cancellation test now checks the group signal. No real Docker daemon was used.
- **Limits:** this is best-effort process-group cleanup, not a complete process-tree or security boundary. A descendant can escape by changing process group/session, and a daemonized or otherwise detached process may survive; successful foreground commands are not followed by group cleanup. Repeated cancellation or cleanup errors can interrupt cleanup. Group signaling does not prove that a Docker container is stopped, because the Docker daemon manages it separately. A subsequent section addresses POSIX background process groups; Windows process trees and macOS have not been addressed or tested. The normal one-second cleanup wait remains bounded if an escaped descendant holds stdout open.

## Completed: POSIX background process-group kill

- Background shell and executable launches now start in a new POSIX session. An authorized `kill_background` sends SIGKILL to its process group, including group members that retain stdout after the original leader exits. Non-POSIX platforms continue to signal only the direct process. Existing task ownership checks run before any signal; normal successful completion does not trigger group cleanup. Starting a new session can change terminal and signal behavior.
- If the group signal fails with an OS error, the executor attempts direct-process kill and reports a warning that only the direct process was signaled. If both signals fail it returns an error without setting `killed`; a missing process group is treated as already absent. Status `killed` is not proof that every descendant has exited.
- Five tests in `tests/test_background_process_group.py` cover a real shell with child and grandchild, an exited leader with a descendant holding stdout, unauthorized kill, and mocked signal failure/fallback cases. Before the change the first two reproduced descendants writing their marker after kill. Existing isolation and output tests passed, as did the mocked Docker launch policy tests.
- **Limits:** POSIX process groups are not a process-tree containment mechanism: processes can escape by creating another session/group, redirecting stdout, or daemonizing. Once a task is marked finished, kill does not target any remaining descendants. Killing the Docker client group does not prove container termination. Graceful server shutdown is addressed below; crash/restart recovery, broader concurrency, Windows/macOS behavior and real Docker remain unverified. The process registry is in memory; group identities can no longer be managed across server restarts.

## Completed: best-effort background cleanup on graceful server shutdown

- The FastAPI lifespan now closes admission for new background starts at shutdown and attempts to stop all running registered tasks across scopes in parallel. It uses the existing trusted internal group-stop path rather than bypassing the public kill tool's scope checks. Startup reopens admission. The shutdown result logs only aggregate counts when cleanup is uncertain or starts remain pending, not commands, task IDs or output.
- Starts already awaiting process creation are tracked. Shutdown waits up to five seconds for those starts; a start that finishes after shutdown began is registered and asked to stop rather than handed to the caller, even if a new lifespan has reopened admission meanwhile. Processes that escaped their group, tasks already marked finished, other workers, Docker containers, foreground commands and CLI/TUI lifecycles are outside this cleanup. ## Completed: shared foreground spawn and execution deadline

- Foreground commands now use a single monotonic timeout budget for awaiting subprocess creation and reading/waiting for its output. If the budget expires during creation, the call returns timeout metadata immediately and a tracked cleanup waits for a late process object and attempts to terminate it. If creation succeeds, only the remaining budget is available for output and process completion. Caller cancellation uses the same late-spawn cleanup path. A spawn coroutine that itself raises `TimeoutError` remains a spawn error rather than being mistaken for the executor deadline.
- Six tests in `tests/test_foreground_deadline.py` cover delayed real subprocess returns in both shell and exec paths, a shared budget across delayed creation and command execution with partial output, normal execution within budget, a late spawn failure and an internally raised spawn `TimeoutError`. - When timeout occurs before the process object is returned, output is explicitly unavailable; `truncated=False` means no output was captured, **not** that the child produced no output. A late-created process may execute side effects before cleanup can signal it. The timeout is cooperative: event-loop stalls and synchronous work cannot be preempted, and post-timeout direct-process cleanup can extend elapsed time. Policy checks and checkpoint work outside the executor's budget are not covered.
- **Limits:** this returns a timeout even if creation remains pending indefinitely, but the background cleanup task can remain pending too; later sections describe a bounded server-shutdown wait for already-tracked cleanup tasks and a per-process foreground admission limit. ## Completed: per-process foreground command admission

- Foreground command execution now reserves one of eight process-local slots before executing command policy or creating a subprocess. ### Windows: a stop request ends the whole process tree (pull request #6; product change by an outside contributor)

- **What changed.** Pull request #6 by an outside contributor (`jin3107`): one commit, `84bc4eb`, merged unchanged on 2026-11-21 (UTC); five files under `engine/`, three test files, no new dependency. The new module `engine/proctree.py` starts the commands of the `run_command` and `run_background` tools, of lifecycle hooks and of the legacy `on_file_change` hook. POSIX behaves as before: the command gets its own session and the stop paths signal the process group. On Windows the process is created suspended, assigned to a new Job Object and only then resumed, so the processes that the command starts are in the job as well. The foreground timeout and cancellation (`_signal_foreground` in `engine/tools.py`), `kill_background` (`_kill_task` in `engine/background.py`) and the hook timeout and cancellation (`_stop_hook_process` in `engine/hooks.py`, `_stop_legacy_process` in `engine/hook_checked_runner.py`) now terminate the job and not only the direct process. If the process cannot be placed in a job, it is ended while still suspended and the start is reported as an error, so a command does not run outside a job.
- **`kill_background` on Windows.** For a running task `_kill_task` terminates the job, waits up to five seconds for the direct process and then up to five seconds for the job to report no live process; when it does, the tool answers `ok: true`. If the job does not report that in time, the stop stays unconfirmed and the answer is `ok: false` ("the command tree is still running after the stop request; retry stop"); a repeated request terminates the job again, also when `cmd.exe` has already exited.

With it, snapshot, undo, fork export and worktree creation store and return file bytes unchanged under `core.autocrlf` and under a workspace `.gitattributes`, and they refuse to run when the line cannot be written. A repository that was created before this change is repaired on its next use; a snapshot that it had stored before that is restored as it was stored, and undo says so in a note.
- **Diagnostic output (#12).** Importing `engine` switches a standard output or standard error whose error handler is `strict` or `surrogateescape` to `backslashreplace` and keeps its encoding. A `print` in an error handler therefore no longer raises `UnicodeEncodeError` when the code page lacks a character; the character is written as an escape.
